# CoffeeBear 数据库规范

> 本文档定义 CoffeeBear 数据库变更、迁移、备份、权限和生产操作规则。

## 1. 基本原则

CoffeeBear 使用 PostgreSQL，数据库迁移以 Alembic 为标准路径。

核心原则：

- 数据库结构变化必须可追溯
- Test 先验证，Production 后执行
- 不把手工修改正式库作为正常开发流程
- 生产数据安全优先于开发便利
- 迁移记录必须进入 GitHub

## 2. 数据事实边界

CoffeeBear 中不同数据承担不同事实责任。

例如：

- 银行流水：真实现金事实
- 发票：真实税务事实
- Open Items：应收 / 应付未结生命周期
- FinanceEntry：国内财务事项

不能因为开发方便，让一个模块重复创造另一个模块已经负责的业务事实。

涉及数据归属不确定时，机器人必须创建 Issue 并等待维护者确认，不能自行设计新的事实来源。

## 3. 标准数据库变更流程

任何结构性数据库修改遵循：

1. 明确业务需求和数据归属。
2. 修改 SQLAlchemy Model / 相关代码。
3. 创建或检查 Alembic migration。
4. 检查 migration 是否只包含预期变更。
5. 在 Test 数据库执行升级。
6. 验证旧数据兼容和新功能。
7. 检查是否需要数据回填。
8. 检查是否存在不可逆操作。
9. Production 发布前完成备份 / 恢复方案确认。
10. Production 执行 migration。
11. 验证 schema、核心查询与业务链路。
12. 在 Issue / PR 中记录结果。

## 4. 禁止事项

默认禁止：

- 未留记录直接手工修改 Production schema
- 为修复测试问题直接改正式数据
- 删除表 / 列但不评估历史数据和回滚方案
- 跳过 Test 直接在 Production 首次执行 migration
- 把正式数据库密码提交 GitHub
- 多个机器人同时生成互相冲突的 migration 而不核对 revision 链
- 修改旧 migration 来掩盖已经在其他环境执行过的历史

如果确实需要 Production 紧急数据修复，必须留下 Issue / 操作记录、影响范围、执行 SQL 或脚本、验证结果和后续修复方案。

## 5. 数据库账号与最小权限

Production 示例配置中区分：

- 数据库 owner / admin
- 应用账号
- migration 账号

原则：

- 应用运行账号只获得业务运行所需权限
- migration 账号只在需要迁移时使用
- 管理员账号不应作为日常应用连接账号
- 密码只存在于受控部署环境，不进入 Git

## 6. Test 与 Production 隔离

Test：

- 使用非生产数据库
- 可以用于迁移验证和必要的测试数据重建
- 不以 Production 数据库作为默认测试环境

Production：

- 只承载正式业务数据
- 迁移、修复、回填都必须有记录
- 禁止为了测试直接写入模拟业务数据

## 7. 高风险迁移

以下变化视为高风险：

- 删除列或表
- 修改主键 / 唯一约束
- 大规模数据类型转换
- 大表全量回填
- 影响财务金额、税务、库存、订单状态的数据重算
- 可能长时间锁表的 DDL

高风险迁移必须额外说明：

- 数据量
- 锁表风险
- 执行时间预估依据
- 是否支持在线迁移
- 备份方式
- 失败恢复方式
- 新旧版本兼容窗口

## 8. 数据备份与恢复

任何可能破坏或大规模修改 Production 数据的操作前，都需要明确可用的恢复路径。

“有备份”不能只停留在口头说明，应能回答：

- 最近一次有效备份是什么时候
- 备份保存在哪里
- 是否验证过恢复
- 恢复需要哪些权限
- 恢复后业务需要做什么校验

如果这些问题无法回答，高风险 Production 数据操作应视为未满足前置条件。

## 9. Migration 冲突处理

机器人发现 Alembic 多头 revision、重复迁移、历史链异常时：

1. 不得随意删除历史 migration。
2. 先检查哪些 revision 已可能进入 Test / Production。
3. 在 Issue 中记录分叉原因。
4. 优先使用可审计的 merge / 新 migration 修复。
5. 经验证后再进入 Production。

## 10. 完成检查清单

涉及数据库的 PR 必须说明：

- [ ] 是否修改数据库结构
- [ ] 是否新增 Alembic migration
- [ ] Test migration 是否成功
- [ ] 是否涉及数据回填
- [ ] 是否涉及不可逆变更
- [ ] Production 是否需要备份
- [ ] 回滚 / 恢复方式
- [ ] 是否更新相关文档

## 11. 记录规则

数据库的重要设计与变更至少通过以下一种方式留下记录：

- GitHub Issue
- Pull Request
- Alembic migration
- `docs/DECISIONS.md`
- 专项数据修复记录

聊天记录不能代替正式数据库变更记录。
