# V1.6.4 — 采购工作台闪屏修复与入库单号可更正

## 本版目标

解决采购工作台「点一下就闪」的核心体验问题，把订单详情从「每次全库预取」改为点查，
并补齐入库单号的人工更正能力（本系统与吉客云两套独立系统，单号靠人工对齐）。

## 1. 采购工作台闪屏

根因不在渲染层，而在工作区页签：`/purchase/workbench` 的 Tab 身份里带了 `order`，
点一张没点过的单会**新建一个顶层页签**，新页签冷挂载连表带详情整块重绘。

- 采购工作台身份回到 pathname，订单切换交给页签内的订单子标签（原本就存在，一直没生效）；
- 页签恢复时按当前规则重算身份并按 `workspace+identity` 去重，避免旧存储留下同身份页签；
- 切单不再先清空详情（原来会塌成「正在读取订单明细…」再撑开，一进一出闪两下），
  改为保留上一张单内容、新数据原地替换，换单期间只在顶部显示细进度条；
- 翻页不再提前清空选中项；列表只在选中行滚出可视区时才回滚位置。

## 2. 订单详情性能

`workbench()` 原先复用 `chain_snapshot`，等于每点开一张单就把 external_purchase_orders、
alibaba1688_orders、全部入库单、结算单、吉客云采购单整表载入（含 raw JSONB 解码），
再在内存里线性找这一张。`_order_row` 的约定本来就是「pf 为空走点查，只服务单条详情」。

- 详情改主键点查（正数查文件订单、负数查工作流副本，沿用 active / referenceOnly 口径）；
- 供应商输入框联想不再触发全量订单聚合，改走 `supplier_name` 索引去重；
- 正品库存（全量入库 − 全量出库）在详情里只算一次，明细行与仓库卡共用；
- 列表的日期筛选改为先筛订单再聚合，时间口径与 `orderDate` 收敛到 `resolve_order_datetime` 一处。

## 3. 缺陷修复

- **「在途订单」指标卡返回 422**：接口层 status 校验正则硬编码且漏了 `transit`，
  而 service 的 `_matches_status` 支持它。正则改为由 `_VALID_STATUSES` 生成。
- **搜索搜不到未分配 SKU 的单**：原先只拼 allocations，补上 1688 原始商品行、耗材明细、备注。
- **详情取人工入库单号抛 AttributeError**：`Alibaba1688Order` 没有 `raw` 字段（杂项在 `raw_payload`），
  外部副本缺失时整张详情 500。抽 `_manual_inbound_no()` 两级兜底。
- 供应商画像、往来单位切换不再整块塌陷重绘，改为保留旧内容 + 顶部进度条 + 换单期间禁点。
- 列表失败时透出后端原因，不再一律「请刷新后重试」。

## 4. 入库单号可人工更正

本系统与吉客云不联通：入库单先在本系统生成，单号再由人工在吉客云建单时手抄保持一致。
写错、后补或吉客云改名都会导致两边不一致，因此开放人工改号。

- 后端 `PATCH /procurement-chain/inbound-documents/{id}/no`，按
  `(document_type, goodsdoc_no)` 唯一口径查重，写审计 `purchase.inbound.no_correct`；
- 入库单详情弹窗新增「改入库单号」，可填更正原因，与「改入库时间」互斥展开；
- 关联与对账走 `document_id` 而非单号，改号不影响已建立的采购 / 发票关联。

## 5. 已知限制

- 「手工入库单」页面（`/supply-chain/receiving/manual`）依赖的三个接口后端从未实现，
  本版如实标注「功能未接通」并禁用提交，不再发送注定 404 的请求；
- 列表接口的状态筛选仍需全量聚合（状态是派生值，无法直接下推 SQL），
  当前订单量下实测约 100ms，订单量上到几百单时再评估。

## 数据库变化

无 migration。

## 风险

- 采购工作台页签身份规则变化：已打开的旧订单页签在恢复时会按新规则合并，
  不影响数据，只影响页签数量（从「每单一页签」变为「一个采购页签 + 订单子标签」）。
